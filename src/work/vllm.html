At work · interactive demo

A multi-GPU LLM deployment manager

A self-hosted control plane that runs several vLLM inference engines on one four-GPU host, each in its own container, behind a single OpenAI-compatible endpoint. An operator registers a model, its GPU and its limits; clients just name it in model, and a stopped one starts on demand.

The code is not public. Below is an interactive demo on made-up data: nothing here talks to a real GPU. It is written from scratch for this page and runs entirely in your browser; the hosts, models, clients and numbers are invented. Screenshots of the real interface follow at the end.

Try it

The manager, in your browser

Start and stop deployments and watch the card's memory budget decide; start one that does not fit; pin a booked one; send a prompt to a stopped model and watch the gateway cold-start it. It starts from the same state on every load, and "Reset demo" brings it back.

Architecture

How it works

  • Two small services. A manager on the host drives Docker; a gateway in a container is the only client of the engines. The UI talks to the manager.
  • One container per deployment. The GPU comes in through device injection, the model cache is mounted read-only, and the flags the scheduler owns (port, parallelism) cannot be overridden.
  • Ready from the logs, not from probes. The manager follows the engine's log until it reports it is up, and reads the measured memory profile from the same stream. A start that hangs past its ceiling is killed and cleaned up.
  • Admission by measured budgets. Each card has a table of measured memory floors against a ceiling, and one start at a time per card. Free memory is read only to refuse a start, never to admit one.
  • Eviction that knows what it may stop. Only idle, lazy deployments go, least recently used first; pinned and reserved ones never. If a start would not fit even then, it is refused before anything stops.
  • A gateway that hides cold starts. It routes by the name in model, asks the manager to make sure it runs, keeps the client's stream alive with comment keepalives, then passes the engine's bytes through untouched.
  • One planner for every promise. Reservations, pins, edits and deletes all go through the same interval check, and a refusal names the item in the way.
  • Docker is the source of truth. After a restart, the manager rebuilds its state from container labels before it admits anything.

Worth a look

What I like about it

  • Two starts can never both see free memory and both run out: admission uses measured profiles, with the engine log first, the driver second and an estimate last, and a stale profile is flagged in the UI.
  • A reservation admitted on an estimate is downgraded to unfulfillable as soon as a real measurement disproves it.
  • The streaming proxy is byte-for-byte faithful to the engine, yet the client never notices a model being loaded.
  • The whole host is declarative: the service, the engine image pinned by digest, and an offline test suite.
